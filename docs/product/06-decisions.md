## 决策 1：工作流引擎的定位 ⭐ 最关键

### 问题

Pipeline DAG（方向 B）是本插件最大跃迁点，但有两条实现路径：

### 选项 A：插件内嵌工作流引擎（推荐）

**含义**：在 `dsh-aigc-canvas` 内部实现 pipeline spec 解析、拓扑排序、执行引擎、断点续跑。

**优点**：
- 中间状态 host 侧持久化，崩溃即丢失的风险低
- 能断点续跑——失败后从断点继续，不浪费已花的钱
- 能并行独立分支（Agent 串行调用无法并行）
- Pipeline spec 可存为模板复用

**代价**：
- 工作量大（约 3-4 周）
- 要做进度 UI、错误处理路径多
- 调试困难

### 选项 B：依赖 DSH 的 plan/subagent 拆解

**含义**：插件只提供原子工具（`aigc_http_request` / `aigc_canvas_place` / `aigc_media_edit`），让 DSH 的 plan 机制拆高层任务、subagent 执行子任务。

**优点**：
- 不增加插件复杂度
- 复用 DSH 已有的规划能力

**代价**：
- 中间状态在 Agent 上下文里，崩溃即丢失
- 不能并行（Agent 串行调工具）
- 不能存模板复用（每次重新拆）
- 失败重试粒度只能整任务级，不能从断点续跑

### 推荐：选项 A

**理由**：
1. 这是"工具集 → 工作环境"跃迁的核心，值得投入
2. AIGC 任务有结构（生图 → 生视频 → 合成），适合用 pipeline 抽象
3. 选项 A 与选项 B 不互斥：Agent 仍可用 DSH plan 拆高层任务，pipeline 处理"AIGC 子任务"

### 折中方案

如果工作量太大，可以分两阶段：
- **阶段 1**：线性 pipeline（不支持任意 DAG，只支持步骤序列）
- **阶段 2**：放开复杂图（fan-out / fan-in）

## 决策 2：语义化边的颗粒度

### 问题

边从 `{source, target}` 升级为 `{source, target, relation}`，relation 用什么形态？

### 选项 A：固定 11 种关系枚举（推荐）

```
input | reference | first_frame | last_frame |
style | mask | audio_track |
variation_of | remix_of | alternative_of | edited_from
```

**优点**：
- Agent 推理清晰（看到固定类型就知道含义）
- UI 渲染统一（每种关系一种线型/颜色）
- 工具 schema 严格（enum 约束）

**代价**：
- 覆盖不全时 Agent 只能选最接近的
- 加新关系要改代码

### 选项 B：自由文本关系

```
relation: string  // Agent 自己写
```

**优点**：
- 灵活，覆盖任何场景

**代价**：
- Agent 难推理（每次看到不同文本要重新理解）
- UI 无法统一渲染（标签长度不一、颜色无法区分）
- 失去结构化优势

### 选项 C：枚举 + 自由 note 字段（备选）

```
relation: enum  // 固定 11 种
note?: string   // 补充说明
```

**优点**：固定类型保证可推理 + note 处理边缘情况

**代价**：稍复杂

### 推荐：选项 A（必要时升级到 C）

**理由**：
1. 11 种关系已覆盖主流 AIGC 场景
2. 固定枚举是 Agent 可推理的前提
3. 不够再加，向后兼容（旧边默认 `input`）

## 决策 3：跨会话资产库的形态

### 问题

资产库（方向 D §6）让用户主动把满意的作品跨会话复用，怎么设计交互？

### 选项 A：主动提升（推荐）

**含义**：元素默认只在会话内。用户右键 → "提升到资产库" → 进入 `~/.dsh/aigc-canvas/library/`，跨会话可引用。

**优点**：
- 用户主动管理，资产库质量高
- 不会堆积垃圾
- 用户对"什么是资产"有明确认知

**代价**：
- 用户要手动提升
- 可能漏掉有用的元素

### 选项 B：自动入库

**含义**：所有 ready 元素自动入库，靠搜索/标签管理。

**优点**：
- 零摩擦
- 不会漏

**代价**：
- 垃圾堆积（失败生成也入库）
- 资产库快速膨胀
- 需要强搜索能力

### 选项 C：自动入库 + 自动归档

**含义**：所有元素自动入库，但 rejected/archived 状态的自动清理（30 天后）。

**优点**：零摩擦 + 自动清理

**代价**：复杂

### 推荐：选项 A

**理由**：
1. AIGC 产物多数是过程性的，自动入库会堆积
2. 主动提升让用户对资产有 ownership
3. 配合"标记为 winner"工作流，自然引导提升

## 决策 4：是否做 Agent 自评

### 问题

是否实现 `aigc_assess` 工具（方向 A §6），让 Agent 生成完自动评估质量？

### 选项 A：做（自评闭环）

**含义**：配一个"评审" provider（视觉模型），Agent 生成完先自评，分数低自动 reroll。

**优点**：
- 真正闭环的 Agent 行为
- 减少 user-in-the-loop 的负担
- 符合"Agent 主题"

**代价**：
- 多花一次 API 成本（评审也要钱）
- 评审模型不一定准（可能误判）
- 增加复杂度

### 选项 B：不做

**含义**：让用户当评审。

**优点**：简单

**代价**：失去"自主质量闭环"的卖点

### 推荐：第二波之后再决定

**理由**：
1. 先把 reroll/variation 做好，自评是锦上添花
2. 评审 provider 配置是额外负担（用户要配视觉模型）
3. 自评准确率依赖评审模型质量，未必可靠

如果做，建议：
- 默认关闭，用户显式开启
- 阈值可配（如 < 60 分自动 reroll）
- 重试次数有上限（默认 3）
- 自评失败时降级为"不评估"（不阻塞主流程）

## 决策 5：Pipeline 第一版的图复杂度

### 问题

如果选择决策 1 的选项 A（内嵌引擎），第一版支持多复杂的 DAG？

### 选项 A：线性序列（最简）

**含义**：steps 必须是线性序列，前一步的输出是后一步的输入。

```
step1 → step2 → step3 → step4
```

**优点**：实现简单、错误处理路径少、易调试

**代价**：不能并行、不能 fan-out（如同时生图 + 配音）

### 选项 B：线性 + 简单 fan-out（推荐）

**含义**：支持多个独立起始分支，但每分支内部线性。

```
step1 ──→ step3 → step4
step2 ──↗
```

**优点**：
- 支持并行独立分支（生图 + 配音同时）
- 实现复杂度可控
- 覆盖 80% 真实场景

**代价**：不支持 fan-in（多个上游汇到一个 step）

### 选项 C：任意 DAG

**含义**：完整的拓扑排序 + 任意 fan-in/fan-out。

**优点**：最灵活

**代价**：实现复杂、调试困难、UI 展示 DAG 难

### 推荐：选项 B

**理由**：
1. 覆盖 30 秒广告片这类核心场景（生图 + 配音并行 → 合成 → 剪辑）
2. 实现复杂度可控
3. 跑通后再放开 fan-in

## 决策 6：Provider Catalog 与旧 instructions 的关系

### 问题

升级为结构化 EndpointSpec（方向 C）后，旧的 `instructions: string` 字段怎么处理？

### 选项 A：并存（推荐）

**含义**：`instructions` + `endpoints` 同时存在，`aigc_get_provider_info` 返回两者，Agent 优先读 `endpoints`。

**优点**：
- 向后兼容（旧 Agent prompt 仍能用）
- 迁移平滑

**代价**：两个字段可能不一致

### 选项 B：完全替代

**含义**：`instructions` 字段删除，只用 `endpoints`。

**优点**：干净

**代价**：破坏向后兼容、迁移突兀

### 选项 C：自动派生

**含义**：`instructions` 字段保留，但 host 从 `endpoints` 自动生成（不可手动编辑）。

**优点**：一致性保证

**代价**：失去自由文本的灵活性

### 推荐：选项 A，长期演进到 C

**理由**：
1. 第一版并存，避免破坏现有用户体验
2. `aigc_provider_set_endpoints` 同时自动更新 `instructions`（从 endpoints 生成简短描述）
3. 下一版禁止手动编辑 `instructions`，只读
4. 最终删除 `instructions`

## 决策 7：成本追踪的数据来源

### 问题

成本追踪（方向 D §5）需要知道每次调用花了多少钱，数据从哪来？

### 选项 A：用户配置固定成本（推荐）

**含义**：provider 配置加 `costPerCall: 0.02`，每次调用累加。

**优点**：简单、可预测

**代价**：不精确（不同尺寸/时长成本不同）

### 选项 B：从响应解析

**含义**：部分 provider 响应包含 `usage.cost` 字段，host 自动解析。

**优点**：精确

**代价**：依赖 provider 返回成本字段，多数不返回

### 选项 C：按规则计算

**含义**：配置 `costPerKiloToken` / `costPerSecond` / `costPerPixel`，host 按响应特征计算。

**优点**：比 A 精确

**代价**：配置复杂、规则维护负担

### 推荐：选项 A 为主，B 补充

**理由**：
1. 选项 A 简单可用，覆盖 80% 场景
2. 如果 provider 响应带成本字段（如 OpenAI usage），自动解析覆盖
3. 不做选项 C（维护成本高，价值有限）

## 决策 8：请求日志的存储与生命周期

### 问题

请求日志（方向 D §3）存哪里、保留多久？

### 选项 A：内存 + 会话隔离（推荐）

**含义**：日志只存内存，会话结束即丢失。

**优点**：简单、不占磁盘、隐私好

**代价**：会话结束后无法回看

### 选项 B：持久化到磁盘

**含义**：`<cwd>/.dsh-aigc-canvas/<sessionId>/requests.log`，跨会话保留。

**优点**：可回看、可导出分析

**代价**：磁盘占用、隐私风险（含请求 body）

### 选项 C：内存 + 可导出

**含义**：内存存储，用户可点"导出"保存到文件。

**优点**：兼顾隐私与可导出

**代价**：用户要主动导出

### 推荐：选项 A，必要时升级到 C

**理由**：
1. 调试场景下会话内回看已足够
2. 内存存储避免隐私风险（请求 body 可能含敏感信息）
3. 如果用户反馈需要持久化，再加导出功能
